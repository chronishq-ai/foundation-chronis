# Sprint 1B — Synthetic Data Test Harness

## Status: Closed

This replaces the original Sprint 1 plan of ingesting real TILES-2018
data. TILES is licensed for approved research use only; Chronis is a
commercial startup, not a research lab, so no real TILES-2018, WESAD,
or other DUA-restricted data has ever been downloaded, mirrored, or
touched anywhere in this repository or its CI environment. Every byte
of sensor data used in this sprint is generated by our own
deterministic, seeded script.

## What was built

All code lives under `synthetic/`, clearly separated from `src/chronis_ml/`
so nobody mistakes fixture data for production code or real user data.

| Module | Responsibility |
|---|---|
| `config.py` | `GenConfig`, `CorruptionConfig`, deterministic participant roster + active-day calendar (including `participant_dropout`) |
| `timeutils.py` | Shared irregular-timestamp and random-window generation |
| `dailystate.py` | Deterministic per-participant-per-day stress intensity, shared (without direct coupling) between generators that want loosely-correlated signals |
| `generators/` | 9 registered stream generators (see below) |
| `registry.py` | The stream-name → generator registry |
| `corruption.py` | 6 of the spec's 8 corruption modes, applied as record/file-level transforms |
| `writer.py` | Writes generator output to the `synthetic_root/<stream>/<group>/<day>.csv` layout |
| `generation_manifest.py` | Writes/reads `_generator_manifest.json` — the generator's own self-description (seed, config, version) for one run |
| `tiles_participant_index.py` | Discovery, probing, stream inference, the file-scanning reproducibility manifest, and cache save/load with invalidation |
| `canonical.py` | 9 per-stream adapters converting raw CSV rows into 4 distinct canonical record kinds (Point / Interval / Event / Snippet) |
| `query.py` | The participant-scoped query API — two-layer isolation defense |

### Registered streams (9, spanning the spec's 8 modality folders)

`fitbit.heart_rate`, `fitbit.steps`, `fitbit.sleep`, `chest_ecg.snippet`,
`audio_features.summary`, `proximity.participant_beacon`,
`environment.device`, `phone_events.interaction`, `surveys.ema`.

## Open items — honestly flagged, not silently resolved

1. **No explicit typed-missing canonical records are ever produced.** The spec's canonicalization rule ("emit typed missing/null state only when the data actually justifies it") implies the system should be *able* to represent an explicit missing reading, the way `chronis_ml.schema.MeasurementStatus.MISSING` does for real GLOBEM/TILES data. In this synthetic harness, missingness only ever shows up as **absent rows** (via `missing_block` corruption or `participant_dropout`) — no generator currently emits a per-cell "this sensor produced no reading" marker the way GLOBEM's real NaN cells do. Every existing code path correctly never zero-fills or interpolates, but the richer "typed missing state" concept from the real schema isn't exercised here at all. Follow-up: decide whether a generator should simulate per-cell sensor dropout (distinct from a whole missing block), and whether `canonical.py`'s adapters should then map that into `MeasurementStatus.MISSING` records using `chronis_ml.schema`'s existing types.

2. **`proximity` only covers the participant-beacon variant.** Beacon-to-beacon and device-to-beacon proximity aren't participant-scoped and don't fit the registry's `generate(participant, day, rng)` signature. They need a separate, non-participant-scoped generation entry point — not built.

3. **`environment.device` assumes one device per participant.** The spec's literal granularity is "per device," not per participant. This is a documented simplification, not a spec requirement.

4. **`fitbit.sleep`'s stage-cycle design has no numbered spec section to verify against** — the spec only mentions "sleep" in its folder table, with no Section-5 ranges. The stage durations/cycle structure are this project's own reasonable design, explicitly documented as such in `fitbit_sleep.py`.

5. **The EMA/HR stress correlation is one-directional.** `EmaSurveyGenerator` consumes the shared `daily_stress_intensity` value; `FitbitHRGenerator` (built in Step 2, before this requirement existed) does not yet consume it. Wiring both to the same latent value is a documented follow-up, not done here, to avoid changing already-shipped, tested Step 2 behavior mid-sprint.

## What changes when real Chronis hardware/pilot data eventually exists

Per spec Section 9 — this harness is a bridge, not a permanent substitute. When real hardware and real pilot participants exist, real ingestion is a **separate, later decision requiring its own review**, not an automatic extension of this sprint's code. At minimum, that later work will need:

- **An explicit consent process** describing exactly what's collected and how it's used, written for and agreed to by actual pilot participants — nothing in this synthetic sprint pre-approves that.
- **A real adapter** written against the real device's actual file/stream format. This will differ from the synthetic schema in this repo — the header names and folder layout in `synthetic/` were invented by this project, loosely inspired by public descriptions of what a multimodal wearable study looks like, and were never claimed to be TILES's or any other dataset's real schema. Only the *pipeline architecture* (canonical adapters, the 4 record kinds, the isolation query layer, the manifest/cache pattern) is expected to carry over — not the literal column names.
- **A deliberate decision on retention, deletion, and internal access** to raw versus aggregated real user data, made at that time by whoever owns that call — not inherited from anything decided in this sprint.

Nobody should let the synthetic schema in this repo quietly become the assumed real schema by default just because it's already built and tested.
